# Quiz Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Registered participants take the quest's quiz one server-timed question at a time. Every attempt is durable and scored on the server into the existing `Result` row. Admins author quizzes, attach variants to the quest, monitor live, void attempts, and correct the answer key before results.

**Architecture:** Two new collections. `quizzes` holds authored content with embedded questions. `quizattempts` holds one document per participant per quest, carrying a frozen snapshot of the exact questions shown. Every participant write is a single-document conditional `updateOne`, and expiry is resolved by a pure `settle` step that runs on every request, in a 60 s sweep, and before ranking. Finalising writes the existing `Result`, so the leaderboard, ranks and certificates don't change. The quest keeps the quiz window and gains `quizConfig` (distribution + quiz ids + seed) and a derived `quizSummary`, replacing the two placeholder fields.

**Tech Stack:** Express 5 + TypeScript (NodeNext), Mongoose 9, Zod 4, pino; React 19 + Vite + Tailwind 4, React Query 5, React Router 8, react-hook-form, lucide-react; new: `@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities` (web only).

**Spec:** `docs/superpowers/specs/2026-11-11-quiz-design.md`. Section references below (§n) point there. Read §7, §8, §10, §11 and §13 before any API task.

## Global Constraints

- **No automated tests** (user's CLAUDE.md). Each task is verified with `pnpm typecheck` plus the `curl`, script or manual checks it lists. `apps/api/src/scripts/quiz-drill.ts` (Task 9) is the concurrency verification tool and is re-run after every later API task.
- **Server is the sole authority.** Participant requests carry only `{ optionId, lock, clientId, signals }`. Never accept a score, a time, an order, a status, an attempt id or a participant id from a participant.
- **Never serialise to participants:** `correctOptionId`, `isCorrect`, `explanation`, `difficulty`, unserved items, other items, `quizConfig.seed`, group/variant labels. Only `GET /quiz/attempt/review` (after `quizClosesAt`) may return the first three.
- Constants are verbatim from §10: `QUIZ_ANSWER_GRACE_MS = 2000`, `QUIZ_MAX_QUESTIONS = 100`, time limit `5–300 s` (default `30`), MCQ options `2–6`, `QUIZ_RESULTS_BUFFER_MS = 300_000`, `QUIZ_MAX_GROUPS = 4`. Text limits: title `120`, description `2000`, prompt `500`, option `200`, explanation `500`, void reason `300`.
- Rank order is unchanged: `score ↓, durationMs ↑, submittedAt ↑, _id ↑`, with `submittedAt = attempt.completedAt`.
- A `Result` is written only for attempts with **≥ 1 item whose outcome is `locked` or `auto`** (§13.4).
- Finalise and re-score **always recompute** `isCorrect` from `selectedOptionId` vs the item's current `correctOptionId` and `voided`. Stored `isCorrect` is display-only.
- Locks key off **attempt existence** (§13.6). Quest `quizConfig`, `quizOpensAt`, and earlier `quizClosesAt` are rejected once the quest has any attempt; quiz content is rejected once any attempt references the quiz.
- All `/quiz` responses: `Cache-Control: no-store`.
- Backend naming: `*.routes.ts`, `*.controllers.ts`, `*.services.ts`, `*.middleware.ts`, `*.model.ts`, `*.validators.ts`. Services return DTOs; controllers speak HTTP via `ok(res, data, status?)` (`utils/respond.ts`); admin mutations call `auditAdmin(req, action, meta)` (`utils/audit.ts`).
- Frontend: feature-first, React Query for server state, Zustand only for cross-tree UI state. Shared presentational quiz pieces live in `apps/web/src/components/quiz/`, so admin preview and participant play don't reach into each other's feature folders.
- Comments are one-line *whys*. Sans display type only.
- No names in logs: attempt id, quest edition, index and counts only.
- Commits end with the `Co-Authored-By` trailer from the session. Stage only the files each task names. One commit per task unless a step says otherwise.

## Review Focus

1. **Numeric positional paths in conditional updates.** Filters and `$set`s like `{ 'items.3.lockedAt': null }` must hit array index 3. Mongoose casts these against the subdocument schema, and a snapshot item missing the field would match `null` too. The snapshot writes **explicit `null`s** for every nullable item field, and all attempt writes go through `QuizAttemptModel.updateOne(filter, update)` with string paths built by one helper, `itemPath(i, field)`. Task 9's drill fires 10 concurrent identical locks and asserts `cursor` advanced exactly once.
2. **A retry loop that outlives the deadline.** A lock retried after `deadlineAt + grace` must stop and refetch state, not spin or surface an error. `withRetry`'s `until` predicate (Task 1) is wired to the deadline in Task 10. Task 10 Step 9 verifies by throttling the network in DevTools past the deadline.
3. **A backgrounded or frozen tab shows a wrong timer.** `requestAnimationFrame` pauses in hidden tabs and Telegram's webview. The timer derives remaining time from `deadlineAt − serverNow()` each frame (never decrements a counter), and the attempt refetches on `visibilitychange`/`focus`/`online`. Task 10 Step 9 backgrounds the tab for 40 s mid-question.
4. **Dev standalone MongoDB has no transactions.** `withTransaction` runs unwrapped there, so finalise's three writes aren't atomic. The order (attempt → Result → `resultWrittenAt`) plus `repairMissingResults` makes that safe. Task 9 Step 6 kills the process between writes (an env-gated `QUIZ_DRILL_CRASH_AFTER_FINALIZE`) and checks the repair.
5. **Two sources answering one question at once (Telegram + web, or two tabs).** The first lock wins. The other gets `409 already_locked` and must refetch, never show an error toast. `BroadcastChannel` may be missing in older iOS webviews, so it's feature-detected. Task 9's drill covers the server side; Task 10 Step 9 opens two tabs.
